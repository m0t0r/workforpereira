# Primary keys are `bigint` identity; public identifiers are UUIDv7

Domain tables use **`BIGINT GENERATED ALWAYS AS IDENTITY`** as the primary key, and rows that are
addressed from outside the system additionally carry a **UUIDv7 `public_id`**, generated in
application code. The internal key never crosses the repository boundary; the domain package speaks
public identifiers only.

## Why

This follows standard Postgres schema guidance — _"Prefer `BIGINT GENERATED ALWAYS AS IDENTITY`.
Avoid random UUIDs (UUIDv4) as primary keys; use `uuidv7()` when you need UUIDs"_ — which holds on
any Postgres and so does not wait on the host choice in issue #4. A `bigint` key is half the width
of a UUID in every foreign key and index, and inserts sequentially. Exposing that
sequential key would leak row counts and invite enumeration, hence the separate public identifier;
UUIDv7 is time-ordered, so the unique index on it stays well-behaved where a v4 would fragment.

## Details worth not rediscovering

- **UUIDv7 is generated in application code, not by a Postgres extension.** Integration tests run on
  PGlite (issue #16), which ships a limited extension set; app-side generation behaves identically in
  Postgres, PGlite, and tests with no database at all.
- **Not every table gets a `public_id`.** Only rows addressed from outside: `persons`, `publications`,
  `offers`. `municipalities` rows are identified by their DANE DIVIPOLA code and `skills` rows by
  their taxonomy slug, and join tables and the contact-exchange log are never addressed individually.
- **`GENERATED ALWAYS` for entities, `GENERATED BY DEFAULT` for reference tables** seeded from
  external data such as the DIVIPOLA list, which needs explicit ids at insert time.

## Rejected: making Better Auth's ids match

`advanced.database.generateId` can produce integer ids (`"serial"`, or the older `useNumberId`), and
Better Auth's tables can be hand-written and adopted. We left it at the default `text` id.

- `"serial"` emits `integer` + `GENERATED BY DEFAULT`, not `bigint` + `ALWAYS` — it adds a third id
  shape rather than unifying two.
- **Better Auth infers `id` as `string` in TypeScript regardless of the column type.** Converting the
  columns would buy cohesion in the DDL and lose it in the types, while introducing a coercion
  boundary in a library that compares ids by string equality.
- A sequential auth id is enumerable, working directly against the reason we added `public_id`.
- `"uuid"` yields `gen_random_uuid()` — v4, the case the guidance above says to avoid.
- Hand-writing the tables means owning `users`, `sessions`, `accounts` and `verifications` through every
  Better Auth upgrade, in the area issue #3 found to be undocumented, to save bytes on columns no
  domain query touches.

The Better Auth tables are a vendored subsystem's schema that happens to share the database. ADR-0002
already isolates the domain from their id shape at a single column.
